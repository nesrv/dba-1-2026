## Слайд 1 — Титул

Тема: **сценарии использования репликации**.

Физика и логика уже знакомы. Сегодня — типовые схемы «под задачу»
и какие параметры включают/выключают, чтобы схема не разъехалась.

Факт: одна и та же streaming-реплика может быть «HA-страховкой»
или «отчётной машиной времени» — разница в `synchronous_*`,
`hot_standby_feedback` и `max_standby_*_delay`.

## Слайд 3 — Физическая репликация (оглавление блока)

Типовые задачи физики:

| сценарий | идея |
|----------|------|
| **HA / горячий резерв** | быстрый failover без потери данных |
| **балансировка однотипной нагрузки** | короткие SELECT на несколько standby |
| **разделение видов нагрузки** | OLTP на master, отчёты на replica |
| **несколько / каскад** | scale-out + разгрузка master |
| **отложенная реплика** | «машина времени» без полного PITR |

Дальше — по одному сценарию с «какими ручками крутить».

## Слайд 4 — Горячий резерв для HA

Цель: реплика почти вровень с мастером; при падении primary —
переключиться **без потери** зафиксированных транзакций.

| сторона | параметры |
|---------|-----------|
| master | `synchronous_commit = on` + `synchronous_standby_names` |
| replica | `hot_standby_feedback = off`, маленький `max_standby_streaming_delay` |

Логика:

- sync — commit ждёт приём WAL синхронной standby;  
- маленький delay — replay сразу, lag минимален;  
- feedback **off** — запросы на реплике не держат vacuum на master.

Запросы на HA-реплике **можно**, но при конфликте их **убивают** —
приоритет у актуальности, не у отчёта. Если SELECT не нужны —
`hot_standby = off` (warm standby).

Нюанс: `synchronous_commit = write` ≠ полная гарантия; `apply` может
тащить лишние задержки. Детали уровней — в модуле про cluster tech.

Репликация — **база** HA, не весь продукт: нужен ещё мониторинг,
авто/полуавто promote, DNS/VIP, чтобы не было split-brain.

---

## Слайд 5 — Балансировка однотипной нагрузки

Цель: короткие OLTP-read на реплике(ах), без отмен из-за recovery.

| параметр | значение | зачем |
|----------|----------|--------|
| `hot_standby_feedback` | **on** | master не вычистит строки, нужные SELECT на replica |
| sync | по политике | можно async, если «чуть устаревшие» ок |

Короткие запросы + feedback ≈ как будто читали с master по горизонту vacuum.
Длинные отчёты сюда **не** кладут — иначе bloat на master.

Балансировку PG **не делает** — HAProxy / PgBouncer / app routing /
модуль «Кластерные технологии».

Между репликами **нет** глобальной read-consistency: два SELECT на A и B
могут увидеть разные эпохи — даже при sync.

---

## Слайд 6 — Реплика для отчётов

Цель: длинные аналитические SELECT **не** бьют master bloat'ом
и **не** отменяются из-за vacuum на master.

Типичный набор:

```text
# на реплике
hot_standby_feedback = off
max_standby_streaming_delay = -1   # конфликты ждут вечно
# часто ещё:
# max_standby_archive_delay = -1
```

На master для этой реплики часто `synchronous_commit = local` —
отчётная нода **не** в sync-кворуме HA.

Мораль двух ручек (повторите вслух):

| ручка | что откладывает |
|-------|-----------------|
| `max_standby_streaming_delay` | **replay** на реплике |
| `hot_standby_feedback` | **vacuum** на мастере |

Для отчётов: feedback off + delay −1 → реплика отстаёт, отчёт доживает,
master чистится спокойно.

Если realtime не нужен — уберите слот, кормите реплику из **архива WAL**:
слот не держит WAL на master вечно. Бэкапы с такой реплики — тоже ок
(с учётом lag).

---

## Слайд 7 — Несколько реплик

К master можно повесить много standby. Спецнастроек мало, но:

- каждый → свой **wal_sender** + обычно свой **слот**;  
- `max_wal_senders` / слоты надо закладывать с запасом.

Развёртывание: одна base backup «размножить» + клонировать слот:

```sql
SELECT pg_copy_physical_replication_slot('replica', 'replica2');
```

Доки: [functions-replication](https://postgrespro.ru/docs/postgresql/16/functions-admin#FUNCTIONS-REPLICATION).

Схема нужна для read-scaling; **кто куда шлёт SELECT** — снаружи Postgres.

## Слайд 8–9 — Каскадная репликация

Master → replica A → replica B: меньше дублей WAL-трафика с primary,
меньше wal_sender на master.

Цена: lag растёт дальше по цепочке.

Важно:

- **sync-каскад не поддерживается** — sync только с прямой standby;  
- feedback с дальних узлов всё равно доходит до master;  
- после failover смотрите **`recovery_target_timeline`** — новая timeline,
  каскадные реплики должны уметь на неё перейти.

Мониторинг нескольких узлов — отдельная головная боль; «просто настроил
и забыл» не работает.

---

## Слайд 10 — Отложенная репликация

«Машина времени» без полного PITR из архива.

```text
recovery_min_apply_delay = '1h'   # пример
hot_standby_feedback = off        # иначе bloat на master
```

Задержка действует на записи **commit**; до commit записи могут
примениться «раньше» — MVCC спасает видимость.

Часы master и replica должны быть **синхронизированы** (NTP), иначе delay врёт.

Инцидент «удалили прод»:

1. данные ещё на delayed-replica;  
2. `SELECT pg_wal_replay_pause();` — заморозить replay;  
3. статус: `pg_get_wal_replay_pause_state()`;  
4. либо `pg_wal_replay_resume()`, либо выставить `recovery_target_*` и перезапуск —
   выйти на момент «до беды».

Быстрее классического restore base+archive, если delay покрывает окно ошибки.

## Слайд 11 — Логическая репликация (оглавление блока)

| сценарий | суть |
|----------|------|
| консолидация филиалов | регионы → центр |
| общие справочники | центр → регионы |
| обновление major | logical bridge между версиями |
| master–master | bi-di (PG 16+) |
| decoding на physical replica | разгрузить publisher |

---

## Слайд 12 — Консолидация данных

Региональные серверы публикуют нужные таблицы → центральный подписан
на каждую (по apply-worker на subscription).

На центре — триггеры нормализации («привести к единому виду»).

Нюансы бизнеса: конфликты ключей, часовые пояса, «что считать истиной».
Иногда batch ETL раз в N часов проще, чем logical 24/7.

---

## Слайд 13 — Общие справочники

Та же схема **наоборот**: центр публикует справочники,
регионы подписываются. Пишут локально свои факты, читают общие коды/тарифы.

DDL по-прежнему руками. Sequences — диапазоны или UUID.

---

## Слайды 15–18 — Обновление основной версии

Физическая реплика **не** переезжает на другую major.
Паттерн с logical (упрощённо):

1. Есть primary 15.x + physical standby 15.x (HA на старой версии).  
2. Поднимаете новый 16.x, logical subscription со старого (initial sync).  
3. Пока клиенты ещё на 15 — догоняете sync; DDL freeze / осторожный cutover.  
4. На 16 поднимаете **новую** physical replica (HA уже на новой версии).  
5. Переключаете клиентов на 16; старый контур гасите.

Это **сложнее**, чем слайд. Sequences, extensions, типы, права —
курс DBA2 «Обновление сервера». Здесь — идея моста: logical = кросс-версия,
physical = HA внутри версии.

---

## Слайд 19 — Master–master

Двунаправленная logical (PG 16+): publish + subscribe одних таблиц на обоих.

Приложение обязано:

- разные **key ranges** или **UUID**;  
- жить без распределённых транзакций Postgres;  
- чинить конфликты **вручную**.

Нет встроенного auto-failover / add-node для multi-master —
оркестрация снаружи. Sync между bi-di узлами ≠ «одна БД».

---

## Слайд 20 — Логическое декодирование на физической реплике

Subscriber тянет изменения не с primary-publisher, а с его **physical standby**.
Цель — снять нагрузку decoding/walsender с мастера.

На replica-publisher:

- `wal_level = logical` (на primary, унаследуется);  
- `hot_standby_feedback` — по политике;  
- при создании слота на standby: **`pg_log_standby_snapshot`** —
  иначе слот/декодирование может «не взлететь» без снимка xmin.

Факт: logical slot на hot standby — мощно, но следите за WAL retention
и за тем, что standby в recovery: нюансы в доках logical decoding on standby.

---

## Слайд 21 — Итоги

**Физическая** — базовый механизм:

- высокая доступность;  
- балансировка однотипных read;  
- разделение OLTP / отчёты;  
- каскад, delay, бэкапы с реплики…

**Логическая** расширяет: выборочные таблицы, кросс-версия, консолидация, bi-di.

Правило лектора: сначала сформулируйте **задачу**, потом выбирайте
вид реплики и параметры. «Включим всё sync + feedback + delay −1» —
не существует, ручки конфликтуют по смыслу.

---

## Слайд 22 — Практика

Кластеры учебного стенда: **alpha**, **beta**, **gamma**.

1. Физическая streaming-репликация **alpha → beta**.  
2. Каскад **beta → gamma** с `recovery_min_apply_delay = 10s`.  
3. Проверить: на gamma данные появляются с задержкой ~10 с.  
4. Остановить alpha, **promote beta**.  
5. Убедиться: gamma остаётся репликой (уже от нового primary / timeline).

После лабы: DROP БД, drop slot, RESET параметров.

---

## Слайд 23 — Практика (детали / практика+)

Типовой каркас alpha→beta:

```bash
sudo pg_ctlcluster 16 beta stop
# очистить PGDATA beta, затем от имени postgres:
pg_basebackup -p 5432 --checkpoint=fast \
  --pgdata=/var/lib/postgresql/16/beta \
  -R --create-slot --slot=replica
sudo pg_ctlcluster 16 beta start
```

`-R` → `standby.signal` + `primary_conninfo` / `primary_slot_name`.

Каскад + delay на gamma: `primary_conninfo` на **beta**, не на alpha;
в `postgresql.auto.conf` / recovery: `recovery_min_apply_delay = '10s'`.

Практика+ из курса: logical decoding на beta / слот на gamma —
`pg_log_standby_snapshot` на beta перед созданием logical slot.

Критерий успеха promote: beta пишет; gamma догоняет новую timeline
без ручного «починить руками пол-PGDATA».

---

## Финал

Пять схем — пять наборов ручек:

1. **HA** — sync on, delay маленький, feedback off;  
2. **OLTP-read** — feedback on, короткие запросы;  
3. **Отчёты** — feedback off, delay −1 (или архив без слота);  
4. **Delay** — `recovery_min_apply_delay` + pause/resume;  
5. **Upgrade / bi-di / decoding на standby** — территория logical.

Физика держит HA. Логика тащит данные туда, куда физика не дотягивается.
В проде часто **оба** контура сразу.

## Слайд 1 — Титул

Так, всем привет. Сегодня не про «красивые SELECT'ы» и не про оптимизацию запросов —
сегодня про то, откуда вообще берётся живой сервер PostgreSQL.

Тема на слайде звучит скучно: «установка и управление».
На практике половина боли продакшена начинается именно здесь:
кто-то поставил не туда, кто-то запустил от root «потому что так проще»,
кто-то забыл `initdb` и удивляется, почему `psql` орёт, что нет кластера,
кто-то обновил пакет и внезапно обнаружил второй инстанс на соседнем порту.

Короче: ставим, инициализируем, стартуем, стопаем.
Без магии — только кнопки, которые реально жмут админы.
Если вы разработчик и думаете «мне это не надо, у нас DevOps» —
всё равно слушайте: в 3 ночи DevOps может быть недоступен, а база — нет.

## Слайд 2 — Темы занятия

План простой, как деплой в пятницу. Идём сверху вниз:

1. **Основные понятия** — чтобы дальше не путать «сервер» и «данные».
   Без этого остальные слайды превращаются в набор команд без смысла.
2. **Сборка из исходников** — когда пакеты уже не спасают, а хочется свой `--prefix`,
   нестандартный порт или «собрать под странное железо».
3. **Управление сервером** — `pg_ctl`, наш швейцарский нож: start/stop/status.
4. **Пакетная установка** — нормальный путь для людей с нервами и для продакшена.
5. **Ubuntu-специфика** — там всё через обёртки (`pg_ctlcluster` и компания),
   и это не баг, а фича дистрибутива.
6. **Облака** — «дайте мне managed Postgres», и что вы при этом теряете.

Если кто-то думал, что «установка = apt install и поехали» — частично прав.
Но мы ещё посмотрим, что под капотом, иначе в проде будете шаманить вслепую.

## Слайд 3 — Кластер БД и сервер

Стоп. Самое важное заблуждение на входе. Закройте ноутбуки на минуту.

**PostgreSQL** — это программа, СУБД.
Когда эта программа выполняется — мы называем её **сервером** или **экземпляром (инстансом)**.
Пока для нас это «чёрный ящик»: принимает соединения, ест SQL, отдаёт строки.
Позже в курсе заглянем внутрь.

**Данные**, которыми он управляет, лежат в файлах на диске — в **базах данных**.
Один экземпляр Postgres одновременно работает с несколькими базами.
Этот набор баз называется **кластером баз данных**.

Запомните мантру и можете набить её на клавиатуре:

> **кластер = данные на диске (файлы)**  
> **сервер / инстанс = процесс(ы), который этими данными рулит**

Путаница со словом «кластер» — классика:
- в Kubernetes «кластер» — оркестрация нод;
- в HA-маркетинге «кластер» — несколько машин;
- в Postgres «кластер» — просто каталог данных + несколько БД внутри одного инстанса.

Один сервер — много баз. Не «одна база = один Postgres», пожалуйста.
Мы не в 2005-м, и лицензия за инстанс тут не кусается так, как у некоторых вендоров.

Подробнее про организацию данных будет отдельная тема.
Сейчас достаточно: прежде чем «ставить сервер», понимать, что потом ещё надо **создать кластер**.

## Слайд 4 — Исходные коды

Зачем собирать из сорцов, если есть пакеты?

Потому что жизнь жестока. Типичные кейсы:

- нужны **нестандартные параметры** `configure` (свой prefix, порт, набор библиотек);
- **специфичная архитектура** / кастомный тулчейн;
- вы разработчик ядра или хотите воспроизвести баг на конкретном коммите.

Два источника исходников:

1. **Tarball** с https://www.postgresql.org/ftp/source — стабильная версия.
   В архиве уже лежат сгенерированные из Flex/Bison `.c`-файлы.
   Распаковал — и можно собирать относительно спокойно.
2. **Git** (`git://git.postgresql.org/git/postgresql.git`, есть зеркала на GitHub) —
   любая точка истории, включая HEAD.
   Но тулов нужно больше: Flex, Bison и компания.
   В git хранятся исходники для генераторов; в tarball — уже результат генерации.

Если вы не разработчик ядра — в ~95% случаев берите пакеты.
Сборка из git — это когда «мне очень надо» или «мне очень интересно»,
а не когда «ну, я же программист, соберу сам в проде».

В учебной ВМ нужный tarball уже лежит у `student` в домашнем каталоге —
не надо качать на семинаре при Wi‑Fi из кафе.

## Слайд 5 — Необходимое ПО

Сборка по классике: **GNU Make + Autoconf**.
С 16-й версии есть ещё **Meson**, но в курсе идём традиционным путём —
так до сих пор собирают очень много продакшен-сборок и так проще читать старые howto.

**Обязательно:**
- `tar`, `gzip`/`bzip2`
- GNU `make`
- компилятор Си (достаточно C89 — Postgres старый волк, не C++20)

**Используются, но можно отключить:**
- **GNU Readline** — редактирование строки, история, автодополнение в `psql`.
  На чистом сервере без интерактивного `psql` можно жить без readline.
  На ноуте разработчика — тащите, иначе консоль будет как блокнот без стрелочек.
- **zlib / lz4 / zstd** — сжатие. Обычно жалко отключать.

**Дополнительно (по необходимости):**
- Perl / Python / Tcl — если нужны PL/Perl, PL/Python, PL/Tcl;
- Kerberos, OpenSSL, OpenLDAP, PAM — аутентификация и шифрование;
- ICU — кроссплатформенный Unicode (сортировки, локали и прочая боль).

При сборке из git список ещё шире — не удивляйтесь, если `configure` начнёт ныть
про отсутствующие штуки, которых в tarball-сборке «как бы уже нет».

Правило большого пальца: ставьте то, что реально будете использовать.
«Поставить всё на всякий случай» — путь к толстому пакету и странным зависимостям.

## Слайд 6 — Демонстрация: сборка из исходников

Демо-режим. Сейчас не теория, а руки на клавиатуре.
Четыре шага — и у вас свой Postgres не из репозитория ОС.

### 1. Распаковка

```bash
cd
tar xzf /home/student/postgresql-16.0.tar.gz
ls -l /home/student/postgresql-16.0
```

Увидите `configure`, `src/`, `contrib/`, `meson.build` и прочий зоопарк — нормально.

### 2. Конфигурация сборки

```bash
cd /home/student/postgresql-16.0
# если пересобираете — сначала:
# make distclean
./configure --prefix=/home/student/pgsql16 --with-pgport=5555
```

`--prefix` — куда положить бинарники (по умолчанию `/usr/local/pgsql`, часто нужен root).
В демо ставим в домашний каталог `student`, чтобы не драться с sudo.
`--with-pgport=5555` — чтобы не поругаться с системным Postgres на 5432.

Если пересобираете с другими флагами — **обязательно** `make distclean`,
иначе получите микс старого и нового конфига и будете долго смотреть в потолок.

### 3–4. Сборка и установка

```bash
make          # можно make world — сервер + расширения + доки
make install
```

`make` — это не `npm install` на пять секунд. Минуты, иногда десятки минут.
Идите за чаем, но не забывайте вернуться.

Расширения из `contrib` при обычном `make` ставятся отдельно:

```bash
cd contrib
make
make install
```

Либо сразу `make world` / `make install-world` — если хотите всё сразу.

Порт 5555 в демо — не «магия безопасности», а чтобы два инстанса не подрались за сокет.
В проде порт выбирайте осознанно, а не потому что в слайде так написали.

## Слайд 7 — Создание кластера (`initdb`)

Бинарники есть — данных ещё нет.
Сервер без кластера — как Docker без volume: процесс можно запустить, смысла мало.

`initdb` создаёт **новый кластер баз данных**. Важные нюансы — прямо про жизнь:

1. **Новый кластер не может принадлежать суперпользователю ОС (root).**
   Postgres специально орёт, если пытаетесь. Это не вредность, это security 101.
   Обычно владельцем делают пользователя `postgres`.

2. **`PGDATA`** — удобная переменная окружения: путь к каталогу кластера.
   Её читают `initdb`, `pg_ctl` и другие утилиты. Меньше `-D /очень/длинный/путь`.

3. **Конфиги создаются в `PGDATA`** (в «ванильной» установке из исходников).
   Про файлы конфигурации будет отдельная тема — сейчас просто факт.

4. **Желательно включить checksums** (`-k` / `--data-checksums`).
   Да, чуть медленнее: при чтении страницы считается контрольная сумма.
   Нет, битые блоки на диске вас не спросят, удобно ли вам сейчас дебажить.

Чексуммы — как seatbelt: бесит, пока не пригодилось.
Потом очень радуетесь, что включили на этапе `initdb`, а не через даунтайм позже.

Доки: https://postgrespro.ru/docs/postgresql/16/app-initdb

## Слайд 8 — Демонстрация: создание кластера

Практика после сборки из исходников.

```bash
mkdir /home/student/pgsql16/data
export PGDATA=/home/student/pgsql16/data
export PATH=/home/student/pgsql16/bin:$PATH

initdb -U postgres -k -D /home/student/pgsql16/data
```

Разбор флагов голосом:

- `-U postgres` — имя **суперпользователя СУБД** (роль внутри Postgres),
  не путать с пользователем ОС. Имена часто одинаковые — мозг плывёт. Не плывите.
  Если `-U` не указать, возьмётся имя текущего ОС-пользователя (`student`).
- `-k` — включить checksums страниц. В проде почти всегда «да».
- `-D` — каталог данных; если задан `PGDATA`, можно не писать, но явно — тоже ок.

После `initdb` в каталоге появится зоопарк: `base/`, `global/`, `pg_wal/`, `PG_VERSION`…
Это и есть «кластер». Поздравляю: вы родили данные.
Сервер ещё не запущен — пока просто аккуратно разложенные файлы.

В проде каталог данных обычно принадлежит отдельному пользователю ОС (`postgres`),
а не вашему личному `student`. В учебной ВМ упрощаем.

## Слайд 9 — Управление сервером (`pg_ctl`)

`pg_ctl` — пульт от инстанса. Основные задачи:

- запуск, останов, статус;
- обновление / перечитывание параметров конфигурации (reload, когда параметр позволяет);
- переключение на реплику (promote) — спойлер на темы про репликацию.

Запускать `pg_ctl` нужно **от имени владельца кластера**.
Не от «ну я sudo и так сойдёт».
Иначе потом права на файлы превратятся в квест «кто всё сломал в 3 ночи».

Это утилита из поставки PostgreSQL — она есть и в сборке из исходников, и в пакетах
(хотя в Ubuntu к ней часто ходят через обёртку — следующий блок слайдов).

Доки для бессонницы:
- https://postgrespro.ru/docs/postgresql/16/app-pg-ctl
- https://postgrespro.ru/docs/postgresql/16/runtime

Документация — ваш друг. Stack Overflow — ваш токсичный друг.
Сначала man, потом Google.

## Слайд 10 — Демонстрация: `pg_ctl`

Минимальный happy path после `initdb`:

```bash
pg_ctl start -l /home/student/logfile
psql -U postgres -p 5555 -c 'SELECT now();'
pg_ctl stop
```

Что важно сказать у доски:

- `-l` — файл журнала сообщений сервера. Без лога дебажить — как чинить прод с завязанными глазами.
- `-D` можно не писать, если задан `PGDATA`.
- В `psql` указываем порт `5555`, потому что так собрали `--with-pgport`.
- Если `SELECT now()` вернул timestamp — сервер жив, вы герой на ближайшие пять минут.
- Если нет — **смотрите logfile**, а не переустанавливайте всё подряд.

`pg_ctl stop` по умолчанию аккуратный. Есть режимы smarter/fast/immediate —
про них потом, когда будем говорить про даунтайм и «почему чекпоинт долгий».

На этом трек «собрал из исходников → поднял → погасил» можно считать закрытым.
Дальше — как делают нормальные люди: пакеты.

## Слайд 11 — Установка пакета

А теперь путь взрослых людей: **готовые пакеты**.

Почему это предпочтительно:

- понятная, поддерживаемая установка;
- обновления через репозиторий (`apt` / `yum` / …);
- меньше шансов собрать «уникальный снежинка-инстанс», который никто не поддерживает;
- пути и сервисы уже согласованы с дистрибутивом.

Пакеты есть почти везде:
- Linux: Debian/Ubuntu, Red Hat-семейство, SUSE…;
- FreeBSD / OpenBSD — ports/packages;
- macOS, Windows — свои истории.

Нюанс: в репозитории ОС часто лежит **не самая новая** версия Postgres.
Актуальную обычно берут из репозитория **PGDG** (PostgreSQL Global Development Group):
https://www.postgresql.org/download/

Мы дальше смотрим **Ubuntu**, потому что учебная ВМ на ней.
На RHEL/CentOS/Alma танцы похожие по смыслу, но другие имена пакетов и другие init-скрипты.
Не копируйте Ubuntu-команды на RHEL «как есть» — получите боль и минус карму.

## Слайд 12 — Создание кластера в Ubuntu

В Ubuntu мир другой. Над `initdb` стоит обёртка **`pg_createcluster`**.

Что важно знать до демо:

- при установке пакета утилита **запускается сама** и создаёт кластер с именем **`main`**;
- **подсчёт контрольных сумм по умолчанию выключен** — классика «удобно из коробки, потом ау»;
- бинарники, конфиги и журнал разложены **по правилам Ubuntu/Debian** (FHS),
  а не всё в одном `PGDATA`, как в ванильной сборке;
- настраивается **автозапуск** Postgres при старте ОС;
- удаление кластера — через **`pg_dropcluster`**.

`pg_createcluster` / `pg_dropcluster` — **специфика Ubuntu/Debian** (`postgresql-common`).
В других системах снова честный `initdb` + свой systemd unit / service.

Справка: `man pg_createcluster` — реально полезный man, не «для галочки».

Мораль: пакет экономит время, но дефолты дистрибутива нужно знать.
Особенно checksums и «где лежат конфиги».

## Слайд 13 — Демонстрация: пакетный Postgres 16

Смотрим живьём то, что уже (или почти уже) стоит в ВМ.

```bash
sudo apt install -y postgresql-16
sudo ls -l /usr/lib/postgresql/16
sudo /usr/lib/postgresql/16/bin/pg_config --configure
sudo ls -l /var/lib/postgresql/16/main
```

Что комментировать:

1. **Установка пакета** — одна команда, и у вас и бинарники, и кластер `main`.
2. **Каталог установки** `/usr/lib/postgresql/16` — `bin/`, `lib/`. Владелец ПО — `root`.
3. **`pg_config --configure`** — длинная простыня флагов сборки пакета
   (OpenSSL, ICU, lz4, zstd, systemd…). Это нормально: пакет собирают «с запасом».
4. **Кластер `main`** уже инициализирован: `/var/lib/postgresql/16/main`,
   владелец каталога — пользователь ОС **`postgres`**.
5. Дальше полезно показать, что **конфиги** в Ubuntu лежат отдельно —
   в `/etc/postgresql/16/main/`, а не только внутри data directory.
   (Точное расположение журнала — на следующем демо.)

Владелец ПО — root, владелец данных — `postgres`. Это нормально.
Не надо панического `chown -R` от тоски.

Если полезли смотреть `base/`, `pg_wal/`, `global/` — отлично для любопытства.
Трогать руками в проде без понимания — быстрый способ устроить себе выходные на работе.

## Слайд 14 — Управление сервером в Ubuntu (`pg_ctlcluster`)

В пакетном Ubuntu к `pg_ctl` ходят не напрямую, а через **`pg_ctlcluster`**.

Зачем обёртка: на одной машине спокойно живут несколько версий (14, 15, 16…)
и несколько кластеров. Нужно явно сказать: *какая версия* и *какой кластер*.

Основные задачи те же:
- запуск, останов, статус;
- перечитывание параметров конфигурации (reload);
- переключение на реплику (promote).

В других системах без `postgresql-common` возвращаемся к честному `pg_ctl`.
Под капотом часто тот же мир — другой UX.

Справка: `man pg_ctlcluster`.

Запомните формулу: **`pg_ctlcluster <версия> <имя_кластера> <команда>`**.
Без версии и имени легко попасть не в тот инстанс — особенно если их несколько.

## Слайд 15 — Демонстрация: управление в Ubuntu

После установки из пакета сервер часто **уже запущен** — systemd не дремлет.
Отдельно стартовать после reboot обычно не нужно.

Управление — от `postgres` или через `sudo`:

```bash
sudo pg_ctlcluster 16 main stop
pg_lsclusters
sudo pg_ctlcluster 16 main start
sudo pg_ctlcluster 16 main restart
sudo pg_ctlcluster 16 main status
sudo pg_ctlcluster 16 main reload
```

`pg_lsclusters` — «что у меня установлено, на каких портах, up или down».
Очень полезно, когда на машине зоопарк из учебных инстансов.

Журнал при пакетной установке:

```bash
ls -l /var/log/postgresql/postgresql-16-main.log
tail -n 10 /var/log/postgresql/postgresql-16-main.log
```

Важная мантра у слайда:

> **`reload` ≠ `restart`**

- **reload** — «перечитай конфиг» (SIGHUP), если параметр это умеет; соединения живы;
- **restart** — «всех выгнать, двери закрыть, открыть заново».

Прежде чем рестартить прод — спросите себя три раза.
Потом ещё раз. Потом сделайте reload, если можно.

В логе после start/reload вы увидите знакомые строки:
`database system is ready to accept connections`, `received SIGHUP`…
Это нормальный heartbeat здорового инстанса.

## Слайд 16 — Облачные решения

Два больших мира — не путать.

### 1. PostgreSQL в своей виртуальной среде (VM / свой IaaS)

- полный доступ к ОС и к экземпляру — можно всё, включая стрельбу себе в ногу;
- есть **накладные расходы виртуализации**;
- для высоконагруженного OLTP лишние слои между СУБД и железом часто нежелательны.

### 2. PostgreSQL as a Service (managed / DBaaS)

- предлагают многие облачные провайдеры (и зарубежные, и российские);
- патчи, часть бэкапов, мониторинг, «кнопки» — на стороне провайдера;
- полного доступа к инстансу обычно нет: вы в песочнице с ограниченным API/UI.

Managed отлично, когда команда маленькая и хочется спать.
Плохо, когда нужно «чуть за пределами меню»: свой extension, особый FS, тонкий тюнинг,
доступ к `pg_wal` руками и прочие радости DBA.

В рамках курса отдельные облака по вендорам не разбираем —
иначе это будет не лекция, а каталог маркетплейса.
Читайте документацию провайдера: грабли у каждого свои.

## Слайд 17 — Итоги

Выжимка для конспекта и для собеса. Можно диктовать под запись:

1. **Два варианта установки** — пакеты (предпочтительно) или исходный код (когда надо).
2. **Доступны облачные решения** — VM с полным контролем или managed с ограничениями.
3. **Сервер выполняется под выделенным пользователем ОС** — не под root.
4. **Перед использованием нужно инициализировать кластер** (`initdb` / `pg_createcluster` / автоматом из пакета).
5. **Специальные команды управления** — `pg_ctl` или дистро-обёртки вроде `pg_ctlcluster`.

Если это отложилось — дальше курс пойдёт легче:
конфиги, архитектура, VACUUM, WAL — всё опирается на «есть инстанс и есть `PGDATA`».

Если не отложилось — вернитесь к слайду 3 и ещё раз про кластер vs инстанс. Серьёзно.
Путаница в терминах дорого обходится в переписке с командой.

## Слайд 18 — Практика: включение checksums

Задача из реальной жизни: пакетный кластер без checksums. Надо включить.

Алгоритм на слайде:

1. Остановите сервер.
2. Проверьте, считаются ли checksums.
3. Включите.
4. Запустите сервер.

Подсказка: утилита **`pg_checksums`**.
В Ubuntu полный путь часто такой: `/usr/lib/postgresql/16/bin/pg_checksums`
(PATH у `sudo`/`postgres` может вас предать — указывайте явно).

Типичные команды (можно наговорить, чтобы не искали потом):

```bash
sudo pg_ctlcluster 16 main stop
sudo /usr/lib/postgresql/16/bin/pg_checksums --check -D /var/lib/postgresql/16/main
sudo /usr/lib/postgresql/16/bin/pg_checksums --enable -D /var/lib/postgresql/16/main
sudo pg_ctlcluster 16 main start
```

На горячую не получится — кластер должен быть остановлен.
Это не баг, это «мы сейчас перепишем meta, не мешайте».

Доки: https://postgrespro.ru/docs/postgresql/16/app-pgchecksums

Если `--check` пишет, что checksums не включены — вы в правильной вселенной пакета Ubuntu.
После `--enable` не забудьте стартануть сервер обратно, иначе «практика» превратится в даунтайм.

## Слайд 19 — Практика+: сборка с нуля

Бонус для тех, у кого ещё не болит голова и есть время до конца занятия.

1. Установите PostgreSQL из исходных кодов так, как в демонстрации.
2. Создайте кластер, запустите сервер.
3. Убедитесь, что сервер работает (`psql`, `SELECT now()`, статус).
4. Остановите сервер.

Важные ремарки голосом:

- команды те же, что в демо, но теперь **своими руками**, без копипасты «в один глаз»;
- `make` может занять от нескольких минут до десятков — это нормально;
- не ставьте второй инстанс на тот же порт/тот же `PGDATA`, что уже занят пакетным;
  у вас как раз для этого был `--prefix` и порт `5555`.

Кто прошёл оба трека — пакетный и из сорцов — уже понимает,
почему в проде почти всегда пакеты,
а «я собрал сам» оставляют для особых случаев, отладки и исследовательского зудя.
